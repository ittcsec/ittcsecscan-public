# Release engineering

Status: **releases are signed offline with a dedicated release key
(ADR-0009).** Nothing is published without a verified signature.

| SLSA provenance | Implemented (`provenance.sh`): `ittcsecscan_VERSION_provenance.json`, an in-toto SLSA v1 statement over the binaries. It is **maintainer-attested**, not builder-attested: its authenticity is the maintainer's offline signature over `SHA256SUMS` (no CI key, no online attestation service), which suits this repo's plan where GitHub's native attestation API is unavailable. **No SLSA level (L1/L2/L3) is claimed**: the provenance uses the SLSA v1 predicate format, but the build is not attested by a SLSA-conformant trusted builder. |

| Archives and installers | Not implemented. Archive timestamps and ordering must be normalised first. |

## Release blockers

These fail the release workflow whenever they apply.

1. **Tenant schema rollback fixtures** (ADR-0012 §4; ADR-0011 rollback tests
   1 and 3).
   - **When it applies:** once `cmd/ittcsecscan` links `internal/store`.
     Today it does not, so `check-schema-fixtures.sh` passes and says why.
   - **What every release then needs:**
     - its schema's frozen fixture, generated by that release's code and
       checked in at `internal/store/testdata/releases/schema-vNNNN/store.db`;
     - the tests `TestReleasedSchemaFixturesMigrate` (test 1) and
       `TestPreviousReleaseReadsCurrentFiles` (test 3), which consume released
       fixtures.
   - **Enforcement:** the build job runs `check-schema-fixtures.sh` for every
     tag and in dry runs.

## Malware scan and false positives

The build job scans every release asset with ClamAV after building. A detection, or any
scan error (including a failure to update signatures), **fails the release job**. There is
no silent skip: a scan that cannot run is a failed release.

A transient signature-update or network failure is not an exception; re-run the job. A
**confirmed false positive** (a ClamAV heuristic firing on a clean Go binary) is handled
as a **reviewed, recorded exception**, never a quiet bypass:

1. Confirm the file is clean: reproduce the byte-identical build (`build.sh`) and, where
   possible, submit the sample to ClamAV as a false positive.
2. Record the exception in this file (date, tag, asset, ClamAV signature name, and why it
   is a false positive), reviewed under the same policy as any other release-affecting
   change (ADR-0008).
3. Scope the allowance to that exact signature and asset for that release only; never
   disable the scan.

## Cutting a release

You need Git Bash (Windows) or any POSIX shell, Go at the version in
`go.mod`, the GitHub CLI, and the release key. Run everything from a
clean checkout of `main`.

1. **Tag.** Make sure the commit is on `main` and CI is green, then push a
   signed tag:

   ```sh
   git tag -s v0.1.0 -m "ittcsecscan 0.1.0"
   git push origin v0.1.0
   ```

   The `release` workflow does the following, then stops:
   - checks the tag format, and that the commit is on `main`;
   - re-runs the tests and govulncheck;
   - builds all six targets twice and requires identical results;
   - adds the SBOMs, the SLSA provenance, the build info, and `SHA256SUMS`;
   - scans every asset with ClamAV (a detection or scan error fails the job);
   - creates an **unsigned draft** release. A `-pre` suffix makes it a
     pre-release.

2. **Sign, offline.** Download the draft and sign it:

   ```sh
   git fetch origin --tags
   gh release download v0.1.0 --repo ittcsec/ittcsecscan-public --dir ../release-v0.1.0
   release/sign.sh ../release-v0.1.0 ~/.ssh/ittcsecscan_release_ed25519
   ```

   `sign.sh` signs nothing unless all of these pass:
   - the key is in the trust root;
   - every asset matches `SHA256SUMS`;
   - the build info names the tagged commit, a clean tree, and your Go
     version;
   - a rebuild of every binary, in a fresh worktree with an empty build cache,
     is byte-identical to the downloaded one.

   Then it asks for the key's passphrase, writes `SHA256SUMS.sig`, and
   verifies it the way a user would.

3. **Upload the signature:**

   ```sh
   gh release upload v0.1.0 ../release-v0.1.0/SHA256SUMS.sig --repo ittcsec/ittcsecscan-public
   ```

4. **Verify on a clean runner, then publish.** Run the workflow from `main`.
   First run with `publish=false` to verify only:

   ```sh
   gh workflow run release.yml --repo ittcsec/ittcsecscan-public --ref main -f tag=v0.1.0 -f publish=false
   gh workflow run release.yml --repo ittcsec/ittcsecscan-public --ref main -f tag=v0.1.0 -f publish=true
   ```

   The `verify-and-publish` job checks, against `main`'s trust root:
   - the signature;
   - every asset;
   - the build info.

   It publishes only when `publish=true` and every check passes. **Never
   publish a draft through the web interface**, because that skips this gate.

Pull requests that change `release/` or the release workflow run step 1
without creating a release (version `0.0.0-dryrun`), and step 2 with a
throwaway key.

## Verifying a release

Put the files you downloaded, `SHA256SUMS`, and `SHA256SUMS.sig` in one
folder. Then, from a clone of this repository's `main` branch (OpenSSH 8.1 or
later; Git Bash on Windows), run:

```sh
release/verify.sh --partial FOLDER
```

It checks the signature against `keys/allowed_signers`, and then checks every
file you downloaded against `SHA256SUMS`. Without `--partial`, every asset
must be present. The equivalent by hand:

```sh
ssh-keygen -Y verify -f release/keys/allowed_signers -I ittcsecscan-release \
  -n ittcsecscan-release -s SHA256SUMS.sig < SHA256SUMS
sha256sum --ignore-missing -c SHA256SUMS
```

To check that the binaries come from the published source, rebuild the tag.
The checksums must match exactly:

```sh
git checkout v0.1.0
SOURCE_DATE_EPOCH=$(git log -1 --format=%ct) release/build.sh 0.1.0 /tmp/verify
diff /tmp/verify/SHA256SUMS <(grep -v '\.cdx\.json$' SHA256SUMS)
```

## Building locally

```sh
SOURCE_DATE_EPOCH=$(git log -1 --format=%ct) release/build.sh 0.1.0 dist
SOURCE_DATE_EPOCH=$(git log -1 --format=%ct) release/build.sh 0.1.0 dist linux/amd64 windows/amd64
```

The script refuses a modified working tree. `ALLOW_DIRTY=1` overrides that for
local experiments; the binary then reports `source_tree: modified`, and
`sign.sh` refuses to sign it.

The inputs that must match for a reproducible build are listed in the header
of `build.sh`: the Go toolchain pinned in `go.mod`, the source tree, the
version string, `SOURCE_DATE_EPOCH`, and the commit.

## Release key custody (ADR-0009)

- The key is a dedicated Ed25519 key, separate from the commit-signing key.
- It is passphrase-protected (`-a 100`) and never added to ssh-agent.
- It never enters CI, GitHub, a synced folder, or any online service.
- Keep it on removable media, with one offline backup in a separate place.
- If it is lost or compromised, follow ADR-0009 "Rotation and compromise".

## TUF update metadata (UP-1)

`release/tuf.sh` generates the signed update
metadata that the client verifies (ADR-0030, `internal/update`). It signs with the
maintainer's offline keys through `ssh-keygen`, so it runs offline on the maintainer's
machine after the binaries are built and signed. The generation and its round-trip
verification against the update client are covered by `internal/update` tests.

### Role expiries and the refresh cadence

`release/tuf.sh` stamps each role with a validity window from the moment of signing:

| Role | Expiry | Why |
|---|---|---|
| root | 365 days | The trust anchor; rotated rarely, through the root-key threshold. |
| targets | 30 days | Pins the release artifacts; re-signed per release. |
| snapshot | 7 days | Pins targets for mix-and-match protection. |
| timestamp | 24 hours | Provides freshness; the shortest-lived role. |

The client refuses metadata past its expiry (`ErrExpired`). The **timestamp expires every
24 hours**, so to keep updates servable the maintainer must re-generate and re-sign at least
the timestamp (in practice, re-run `tuf.sh` to refresh timestamp and snapshot) **daily**, or
on whatever cadence is shorter than the timestamp window. This daily-signing burden is the
practical cost of offline timestamp keys; see the single-maintainer limitation in
`docs/known-limitations.md`.

### What a missed signing window does (fail-closed)

If the timestamp expires before it is re-signed, `update check` and `update install` **fail
closed**: `Client.VerifyChain` returns `ErrExpired` before any target is listed or installed,
so the update command aborts with a non-zero exit and serves nothing. It never silently skips
the check or falls back to stale metadata. The failure mode of a missed window is "updates
are temporarily unavailable and the client says so," never "the client proceeds on expired
metadata."

### Online timestamp and snapshot keys (decided)

**Decision (final): the timestamp and snapshot roles are signed by online automation keys;
the root and targets roles are signed by offline keys only.** This is the standard TUF split
and it is settled, not open. An automated, network-reachable key re-signs the two short-lived
roles on a schedule so no human has to sign by hand every 24 hours; root and targets, which
authorize the actual binaries and the trust anchor, never leave offline keys.

The rationale: a key that can only sign timestamp and snapshot cannot ship a malicious target
or change the trust root. Its worst case is withholding or replaying update metadata within the
existing freeze window (the client still refuses anything older than it has trusted, and
targets are still pinned by the offline-signed targets role). That bounded risk is smaller than
the real failure mode of an all-offline design: one person required to hand-sign every 24 hours
indefinitely, where a single missed day silently breaks updates for everyone with no attacker
involved. So the online split is the safer resting state, and it is what this project uses.

Consequences:

- **Key custody.** Root and targets keys stay offline (UP-7 below). The timestamp and snapshot
  keys are automation keys: passphrase-less or agent-loaded so an unattended job can sign,
  network-reachable, and rotated and monitored on their own schedule. They are authorized only
  for their two roles in the root, so their compromise is contained.
- **Cadence.** The automation re-signs snapshot and timestamp on a schedule shorter than the
  timestamp's 24-hour window (targets is re-signed offline only when a release changes it).
- **Follow-up (UP-8).** The automated snapshot-and-timestamp-only refresh path is the remaining
  implementation of this decision. `release/tuf.sh` today signs all four roles in one offline
  run (used for a full release); the scheduled refresh needs a mode that re-signs only snapshot
  and timestamp against the current targets, using the online keys. Until that lands, the
  interim commitment is a fixed daily signing schedule with a named backup signer and an expiry
  alert, tracked in `docs/known-limitations.md`.

### One-time offline root-key ceremony (UP-7)

Status: performed for `v0.1.0-rc.1`. The four offline keys were generated and signed the TUF
metadata shipped with that release. What remains is client-side wiring (a hosted endpoint and a
pinned root in the binary), tracked as UP-1; until then the updater is inert by design. The
procedure below is the canonical, repeatable ceremony.

Before the first release that ships updates, create the four keys offline and record the
trust root. Do this on an offline machine; the private keys never touch CI or any online
service.

```sh
# One key per role. Passphrase-protect each (-a 100) and never add them to ssh-agent.
for role in root targets snapshot timestamp; do
  ssh-keygen -t ed25519 -a 100 -C "ittcsecscan-tuf-$role" -f ~/.ssh/ittcsecscan_tuf_$role
done
```

Then:

- **Publish the root trust anchor.** The pinned `root.json` the client is built against is
  produced by the first `tuf.sh` run; record its key ids and treat it like the release
  trust root (`keys/allowed_signers`).
- **Back up every private key.** Keep each on removable media with one offline backup in a
  separate physical location, exactly as for the release signing key (ADR-0009). Losing the
  root key without a backup forces a trust-root change; losing a lower-role key is recovered
  by rotating that role in a new root.
- **Rotation.** Rotate the root through the root threshold (`UpdateRoot` requires a
  threshold of both the old and new root keys). Lower roles are rotated by issuing a new
  root that lists new key ids.

Generate a release's metadata with:

```sh
release/tuf.sh 1.0.0 ../release-v1.0.0 ../release-v1.0.0/tuf \
  ~/.ssh/ittcsecscan_tuf_root ~/.ssh/ittcsecscan_tuf_targets \
  ~/.ssh/ittcsecscan_tuf_snapshot ~/.ssh/ittcsecscan_tuf_timestamp
# ssh-keygen prompts for each passphrase; it writes tuf/{root,targets,snapshot,timestamp}.json.
```

Serve the four `tuf/*.json` files from the update endpoint the client fetches metadata from
(`internal/update`). Do **not** add them to the GitHub release before it is published: the
`verify-and-publish` job runs `release/verify.sh` in strict mode, and `check_sums` rejects any
file in the release directory that is not `ittcsecscan_*`, `SHA256SUMS`, or `SHA256SUMS.sig`, so a
`root.json` (or the other three) attached to the release would fail verification. If you do want a
copy attached to the release for distribution, upload it only after `publish=true` has verified
and published, never before.
